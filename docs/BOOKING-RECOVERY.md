# Booking recovery

Apply the schema before deploying the API. From `server`, run `npm run migrate:integrity` against the intended database. The runner installs `20261118_booking_recovery.sql` after the booking integrity migration in the same transaction. The normal `npm run migrate` bootstrap also installs it. Use an isolated database for each verification run. The recovery migration adds booking request hashes, the renewed hold time, reconciliation scheduling and counters, and the booking order intent table. Existing booking and Razorpay IDs are preserved.

The browser keeps a customer-scoped attempt key and a hash of the submitted details for up to 24 hours. Repeat the same selection to reuse the key after reload. The API accepts it in the `Idempotency-Key` header. Other clients may omit the header, in which case each request is a new attempt. The server scopes keys to the customer, binds them to the normalized request and persists a claim before an online order can be created. The booking UUID is the Razorpay receipt. A repeated order request searches by the exact receipt first. If the receipt is absent, retries use that same receipt after a database-enforced cooldown. Older unlinked intents are visible for review and never submit an order on their own. A successful booking-create replay includes the booking and directs the browser through the payment check.

In **My Bookings → Recovery & Refunds**, the customer can resume or release an interrupted checkout. Both operations check the original Razorpay order and payments on the server before taking the schedule and booking locks. Captures go through the same finalization path as a signed callback or webhook. A failing, inconsistent or unresolved gateway response yields `PAYMENT_CHECK_PENDING` without checkout details. Only an order with no payment attempts or fully accounted for failed attempts can be reopened. An expired hold can be renewed after a fresh availability and travel check. A cancellation that races with a later capture produces a refund instead of restoring the reservation.

Recovery reuses the original non-partial order. Razorpay rejects more payments on a paid order. The service also records a separate refund intent for an unexpected additional capture. For a renewed hold, a payment created before or during the renewal second cannot claim the slot. Keep the database clock synchronized. Razorpay returns whole-second timestamps, so a payment created in the same second as renewal is conservatively refunded. A payment first observed after hold expiry can be refunded even if its capture preceded expiry.

Razorpay references: [create order and receipt rules](https://razorpay.com/docs/api/orders/create/), [lookup by receipt](https://razorpay.com/docs/api/orders/fetch-all/), [payments for an order](https://razorpay.com/docs/api/orders/fetch-payments/).

# Operations

- Configure matching Razorpay server and browser keys, auto-capture, and a webhook secret. Configure signed `payment.captured`, `order.paid` and refund events on `/api/bookings/webhook`. Use test mode for verification.
- The API runs reconciliation every 30 seconds when credentials are configured, outside `NODE_ENV=test`, unless `PAYMENT_RECONCILIATION_ENABLED=false`. Multiple API instances and the optional `npm run reconcile:payments` command share a PostgreSQL lease. The standalone command can submit queued refunds against its configured gateway, so use test configuration during local verification.
- With an administrator session, query `GET /api/bookings/recovery/health`. Check the last clean and failed runs, recovery and failure counters, oldest outstanding refunds and incomplete order intents. A stale clean timestamp, repeated failures or an aging queue warrants investigation. Look for `booking_reconciliation_finished` and `booking_reconciliation_failed` structured events.
- A refund intent starts as requested. Only gateway confirmation marks it processed. A lost refund submission response is checked by its receipt and may need manual review when the result remains uncertain. Inspect the refund ID and booking ID in the admin response and compare against the Razorpay dashboard before acting. Never manually submit a second refund solely because the first response timed out.
- Older unlinked intents may require dashboard review using the booking UUID receipt. The order lookup can recover an order ID, but an available slot and a customer retry are required to create the booking. A stored order ID alone does not reserve a slot.

# Local verification

1. Apply the migration to a disposable PostgreSQL instance. Run the booking integration suite with `BOOKING_TEST_DATABASE_URL` pointed at that instance.
2. From `client`, run `npm run build` and then `npm run preview -- --host 127.0.0.1 --port 5198`. In another shell run `node scripts/verifyBookingRecovery.mjs`. It intercepts the API and checkout in Chromium and does not contact Razorpay.
3. With controlled fixtures, create one online booking and one cash booking. Simulate a lost create response and repeat the same selection after refresh. Check that only one row and one online order exist.
4. Simulate a captured payment without delivering the callback. Open Recovery & Refunds and check the booking. Repeat with an authorized payment and a gateway timeout. Both should ask the customer to wait and offer no checkout.
5. Simulate a decline, then retry the same order. Expire its hold and occupy the slot with another booking. The old booking must report the conflict. Capture a payment after cancellation and check that the refund remains pending until the mock gateway returns processed.
6. Check the administrator health response after a successful reconciliation pass and after a forced gateway failure.
